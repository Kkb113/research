# Limits, failures and decision gates

E2 preserves the evidence selected by an optional production CPU preprocessing stage. It does not improve labels, infer new windings, trace new sheets or recover ink. The orientation loss itself is disabled by default upstream and its usefulness is a separate question.

## Execution boundary

The full GPU optimizer was not executed. Runpod's connected skill files were readable, but no Runpod control actions, runpodctl executable or CLI key configuration were exposed in this chat. No GPU resource was provisioned or billed. This is not a claim that the plugin is uninstalled. No independent AI research agents, qualified annotators or expert timing study participated.

## Data and independence

Inputs are model-generated fiber predictions from four real scan volumes, not raw-CT truth labels. Eight hash-selected chunks per volume form the fixture corpus; one Paris4 chunk is development-only for selection tests. The HTTP mirror advertises only that subset, retaining the actual bytes and coordinate scales. It is not a whole-scroll network benchmark.

E1's recorded local source was not recovered. E2 is a new frozen implementation; previous-session inspection of the fixed corpus cannot be certified. Therefore this is fixed-corpus validation, not a newly untouched independent efficacy test. Four volumes demonstrate processing compatibility, not that a learned reconstruction method generalizes.

## Retained regressions

Block selection beats upstream on 28/31 cases and sparse sorting on 23/31, locally and externally. Very sparse/empty chunks can favor sparse sorting. Streaming can be slower than block-only on small extraction jobs. It remains optional.

The largest writer experiment repeats real batches 128 times: 17,279,232 records are a resource load, not new regions. The raw spool requires approximately 247 MiB plus the archive. One measured writer invocation per size does not establish a compression-speed advantage. Linux total-process peak RSS is compared, not a selectively subtracted allocation figure.

## Memory correction

Initial ru_maxrss values inherited parent pre-exec high-water accounting and could not distinguish methods. They remain in `selection_timing.json` and `selection_summary.json` solely for audit. **Do not use those rss_mib fields for comparisons.** Use `selection_memory_corrected.json` (Linux VmHWM). The correction did not change algorithm, cases, thresholds or primary times.

Tiling bounds dense reduction tiles, not total memory. Output coordinates must still exist. Streaming bounds retained output batches, but S3 key sets/work lists still scale with chunk count, temporary disk scales with output, and the upstream NPZ loader still loads arrays. This is not a constant-memory reconstruction pipeline.

## Compatibility and statistics

Python 3.13.5 and pinned CPU computational dependencies were used. This standalone module test does not validate every dependency of villa's Python>=3.14 GPU project. Linux was tested; no Windows/CUDA/VRAM claim is made. Atomic no-clobber publication uses a same-filesystem hard link. The patch rejects upstream hash drift.

Timing uses loopback HTTP, not public-network performance. Hardware/storage/process environments differ. Repeated calls are not independent scrolls. Optional descriptive bootstrap intervals condition on four per-volume effects and fixed sampled chunks; only four clusters support them, so they are not universal population guarantees or acceptance gates.
